# 聊天记录存储方案（后端存储 + 多端同步）

## 概述

本方案分两个阶段实施：
- **阶段一（短期记忆）**：滑动窗口 + 实时落库，解决内存累积问题
- **阶段二（长期记忆）**：实体追踪 + RAG 检索，解决长期歧义问题

---

## 现状分析

### 前端现状
- `page.tsx` 使用 `useState` 管理消息列表，仅存在于内存
- 刷新/关闭后聊天记录丢失
- 已有 `sessionId` 机制（`api.ts:20`），但未用于历史记录获取

### 后端现状
- `/api/chat` 接口接收 `session_id` 参数，但不使用
- 无消息存储层
- FastAPI + Pydantic 架构

---

## 阶段一：短期记忆

### 1.1 目标

- 防止内存累积导致 OOM
- 消息实时落库，不因页面刷新丢失
- 支持会话恢复

### 1.2 整体架构

```
前端 (page.tsx)
    ├── 页面加载时 → GET /api/sessions/{sessionId}/history → 恢复消息
    ├── 发送消息时 → POST /api/chat (带 sessionId) → 后端存储
    └── 组件卸载时 → 可选：标记会话为不活跃

服务端内存
    └── 滑动窗口：保留最近 N 条消息（可配置上限）

后端存储层
    ├── Session 表：会话元信息
    ├── Message 表：消息内容
    └── API 层：历史记录获取接口
```

### 1.3 滑动窗口设计

#### 窗口参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| window_size | 50 条 | 内存中保留的消息条数上限 |
| max_tokens | 16000 | token 上限（可配置） |
| preserve_ratio | 0.5 | 超限后保留比例 |

#### 超限裁剪策略

```
当消息条数 > window_size 时：
1. 丢弃最早的 50% 消息
2. 保留最近的 50% 消息
3. 丢弃的消息已实时落库，不影响恢复

示例：
窗口 50 条，已达上限，用户发送新消息
→ 保留最近 25 条 + 新消息 = 26 条
→ 丢弃的 25 条已在 DB 中，可恢复
```

#### Token 超限判断

```
估算公式：
- 中文：1 token ≈ 1.5 字符
- 英文：1 token ≈ 4 字符

16K 模型：约 16000 tokens
- 可容纳：约 8000 汉字 / 100 条普通问答

触发时机：发送消息前检查，超限则裁剪后发送
```

**写入策略**：每条消息**实时写入**数据库

- 助手消息：流式生成完成后存储

### 1.7 前端改造（阶段一）

**page.tsx 改造点**：
1. `sessionId` 生成逻辑：优先从 URL/Storage 读取，否则生成新的
2. `useEffect` 页面加载时调用 `GET /api/sessions/{sessionId}/history` 恢复消息
3. 消息发送时将 `sessionId` 传给 `sendChatMessage`
4. 新增"清空会话"按钮（调用 `DELETE /api/sessions/{sessionId}`）

**存储介质选择**：
- `sessionId` 存 `localStorage`，实现刷新后恢复
- 跨设备同步需登录，后续迭代

### 1.8 内存安全保证

```python
class SessionMemory:
    """会话短期记忆管理器"""

    def __init__(self, window_size: int = 50):
        self.window_size = window_size
        self._memory: list[Message] = []

    def add(self, role: str, content: str) -> None:
        self._memory.append({"role": role, "content": content})
        self._trim_if_needed()

    def _trim_if_needed(self) -> None:
        """超过条数限制时，裁剪早期消息"""
        if len(self._memory) > self.window_size:
            keep_count = int(len(self._memory) * 0.5)
            self._memory = self._memory[-keep_count:]

    def get_recent(self, limit: int = 50) -> list[dict]:
        """获取最近 N 条消息（防极端情况）"""
        return self._memory[-limit:]

    def clear(self) -> None:
        self._memory = []
```

### 1.9 阶段一数据流

```
用户打开页面（sessionId=abc123）
  → 前端检查 localStorage，有则使用，无则生成并存入
  → 调用 GET /api/sessions/abc123/history
  → 后端返回空列表 []（新会话）或历史消息
  → 前端 setMessages 恢复 UI

用户发送："我想给孩子买保险"
  → 前端：POST /api/chat { message: "...", sessionId: "abc123" }
  → 后端：
      1. 存储 user message 到 DB
      2. 调用 orchestrator.run_chat_flow()
      3. 流式返回 SSE 事件
      4. onDone 时存储 assistant message 到 DB
  → 前端：onDelta 追加到 messages，onDone 时更新 isStreaming=false

超限场景：
  → 内存中消息超过 50 条
  → 裁剪保留最近 25 条，早期 25 条已在 DB
  → 后续需要时从 DB 恢复
```

## 阶段二：长期记忆

### 2.1 目标

- 记住尽量久远的细节
- 解决时序歧义问题（如用户信息变化）
- 不影响响应速度

### 2.2 核心方案：实体追踪 + RAG 检索

#### 问题分析

单纯 RAG 会有时序歧义问题：

```
时间线：
一年前 ────── 半年前 ────── 现在
李四 70kg      李五 60kg     李四 65kg

用户问："我现在多少公斤？"
单纯向量检索结果：
- "李四 70公斤" （相似度 0.85）
- "李五 60公斤" （相似度 0.82）
- "李四 65公斤" （相似度 0.85）
→ LLM 困惑：到底哪个是现在的？
```

#### 解决方案架构

```
用户提问
    ↓
┌─────────────────────────────────────────────────────────┐
│  意图识别层                                              │
│  - 提取实体：姓名、体重、年龄、险种偏好等                   │
│  - 判断问题类型：是问"当前状态"还是"历史变化"               │
└─────────────────────────────────────────────────────────┘
    ↓
    ├── "我现在多重？" → 查实体状态表（直接回答）
    ↓
    ├── "和去年比身体有什么变化" → 向量检索 + 时序分析
    ↓
    └── "上次买的是什么保险" → 混合：实体表 + 消息检索
```

### 2.3 实体追踪层

#### 提取的实体类型

| 实体类型 | 示例 | 用途 |
|----------|------|------|
| 个人信息 | 姓名、年龄、性别 | 基础信息 |
| 身体状况 | 体重、身高、健康状况 | 健康险核保 |
| 家庭信息 | 家庭成员、子女年龄 | 家庭险规划 |
| 财务状况 | 年收入、预算 | 预算筛选 |
| 保险偏好 | 已购险种、期望保障 | 产品推荐 |
| 购买记录 | 何时购买、何种产品 | 续保/加保建议 |

#### 实体状态存储

**user_entity_states 表**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | SERIAL | 主键 |
| session_id | VARCHAR(64) | 关联会话 |
| entity_type | VARCHAR(32) | 实体类型（name/weight/age 等） |
| entity_key | VARCHAR(64) | 实体名称（李四/体重等） |
| value | TEXT | 实体值（65公斤） |
| valid_from | DATETIME | 生效时间 |
| valid_to | DATETIME | 失效时间（NULL 表示当前有效） |
| created_at | DATETIME | 创建时间 |

**数据示例**：
```
张三的实体状态变化：

| entity_type | entity_key | value | valid_from | valid_to |
|--------------|------------|-------|------------|----------|
| name | 张三 | 张三 | 2025-06-01 | NULL |
| weight | 体重 | 80公斤 | 2025-06-01 | 2025-09-01 |
| weight | 体重 | 85公斤 | 2025-09-01 | NULL |
| age | 年龄 | 30岁 | 2025-06-01 | NULL |
```

#### 实体提取时机

| 时机 | 说明 |
|------|------|
| 用户消息进入时 | 分析是否包含可提取的实体 |
| 助手回复完成时 | 提取关键决策信息（如推荐了什么产品） |
| 实体值变更时 | 写入新记录，标记旧记录失效 |

#### 回答策略

| 问题类型 | 处理方式 | 示例 |
|----------|----------|------|
| 问当前状态 | 直接查实体表 | "我现在多重？" → 查 weight=85 |
| 问历史变化 | 实体表 + 时序对比 | "和去年比体重有什么变化？" → 85kg vs 80kg |
| 问具体事件 | 向量检索 | "去年6月买的是什么保险？" → 检索消息历史 |

### 2.4 向量检索层

#### 适用场景

| 场景 | 检索策略 |
|------|----------|
| 需要历史上下文 | 限定 session + 时间范围 |
| 模糊问题 | 语义相似度匹配 |
| 跨实体关联 | 实体关系图谱（可选） |

#### 向量化时机

| 时机 | 优点 | 缺点 |
|------|------|------|
| **实时 + 异步双写** | 数据不丢，不影响主流程 | 有 20-50ms 延迟 |

```python
    msg = await db.insert_message(session_id, role, content)
```

#### 检索增强机制

```
用户问题："当时那个保险的保障范围是什么"

检索过程：
1. 定位相关消息：包含"保险"、"保障"的历史消息
2. 限制时间范围：聚焦提问前的 N 条消息
3. 时间加权：近期消息相似度 × 1.2
4. 结果去重：避免同一事件的重复召回
5. 过滤低相关：相似度 < 0.7 的丢弃
```

```python
# 时间衰减因子：最近 7 天权重 1.0，每往前 30 天降低 0.1
# 实现：1 - (embedding <=> $1) * time_weight(created_at)
```

### 2.5 两层协作模式

#### 协作流程

```
用户提问："我现在还能买百万医疗险吗"

    ↓
意图识别：用户当前状态是否满足投保条件

    ↓
┌─────────────────────────────────────┐
│  实体追踪层                          │
│  - 年龄：35岁                        │
│  - 体重：85公斤                      │
│  - 已有保险：无                       │
│  - 健康状况：良好（从对话历史推断）    │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│  向量检索层                          │
│  - 查找百万医疗险的投保条件            │
│  - 历史对话中关于健康告知的内容        │
└─────────────────────────────────────┘
    ↓
组合回答：
"根据您的情况，35岁、85公斤、健康状况良好，可以投保百万医疗险。

```

#### Prompt 组装优先级

```
┌─────────────────────────────────────────────────────────┐
│  Prompt 组装顺序（从上到下优先级递减）                     │
├─────────────────────────────────────────────────────────┤
│  1. 当前最新实体状态（精确）                              │
│  2. 最近 N 条对话消息（局部上下文）                       │
│  3. 相关度高的历史消息（向量检索结果）                     │
│  4. 系统提示（如投保须知）                               │
└─────────────────────────────────────────────────────────┘
```

### 2.6 多跳推理支持

```
用户问："上次给我推荐的那个保险，现在还能买吗？"

处理：
1. 实体层：找到"上次推荐的保险"对应的产品名
2. 向量层：找到该产品的详细介绍消息
3. 整合：产品信息 + 当前是否在售 → 组合回答
```

### 2.7 冲突信息处理

```
用户说："我之前说体重80公斤，现在要更新成85公斤"

处理：
1. 写入新实体记录：weight=85公斤, valid_from=现在
2. 旧记录标记：weight=80公斤, valid_to=现在
3. 向量层同步更新（避免新旧消息混淆）
```

### 2.8 历史消息归档策略

| 消息类型 | 处理方式 |
|----------|----------|
| 包含关键实体的消息 | 永久保留，向量化 |
| 普通对话消息 | 保留 90 天，超期后只保留摘要 |
| 已提取实体的消息 | 可降级存储（节省空间） |

## 注意事项

1. **隐私合规**：用户消息包含个人信息，建议会话数据加密存储
2. **清理策略**：可定期清理超过 30 天不活跃的会话
3. **SSE 兼容**：历史记录接口不走 SSE，仅普通 REST
4. **向后兼容**：无 sessionId 时走原有逻辑（新会话）
5. **向量延迟**：向量化异步执行，避免影响主流程响应时间

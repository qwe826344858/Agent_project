# 技术方案设计（未完成）

状态：未完成（已完成第一版初稿）

## 一、文档目标与范围

### 1. 目标

1. 支撑阶段一MVP上线，快速验证 Search-First 模式可行性。
2. 提供可执行的技术落地方案，覆盖前后端、模型编排、搜索编排与基础运维。
3. 明确阶段一边界，不引入阶段二及以上复杂能力（如长期记忆、产品数据库、向量检索）。

### 2. 范围

1. Web端对话式保险问答。
2. 核心能力：问答、联网搜索、来源溯源、流式输出、智能追问。
3. 不含：用户登录体系、支付、文件上传、知识图谱、专家对接。

## 二、总体架构

### 1. 架构概览

系统采用前后端分离 + 外部模型/搜索服务调用的轻量架构：

1. 前端（Next.js）：
   - 聊天UI与流式渲染
   - 推荐问题展示
   - 思考状态提示
2. 后端（FastAPI，阶段一主框架）：
   - 接口层（`/api/chat`、`/api/suggestions`）
   - 编排层（意图识别 -> 搜索词生成 -> 搜索 -> 汇总生成）
   - 输出层（SSE流式推送 + 来源链接拼装）
3. 外部服务：
   - LLM API（回答生成、问题拆解）— OpenAI 兼容协议，API 端点 `https://api.minimaxi.com/v1`，模型 `MiniMax-M2.5-highspeed`
   - 保险平台直连 API（小雨伞/平安/慧择，产品搜索与结构化数据获取）
   - fallback 静态知识库（通用保险知识，替代原搜索引擎通用搜索）

### 2. 分层设计

1. 表现层（Frontend）
2. 接口层（API Gateway/Controller）
3. 业务编排层（Orchestrator）
4. 能力层（LLM Client、Search Client）
5. 观测层（日志、指标、告警）

## 三、模块设计

### 0. 后端框架选型（阶段一结论）

阶段一后端主流框架统一为 `FastAPI`，不采用多框架并行。

选型理由：

1. 阶段一目标是快速验证，FastAPI在接口开发与迭代速度上更有优势。
2. Python生态更适合LLM编排、Prompt调优、文本处理与后续RAG扩展。
3. 当前主要耗时在外部搜索与模型调用，瓶颈不是Web框架本身。
4. FastAPI原生支持异步与类型校验，适合SSE流式与API快速联调。

### 0.1 编排框架演进策略（轻方案 -> LangGraph）

阶段一采用轻方案快速落地，但从第一天按“可替换编排层”设计，避免后续大面积改动。

设计原则：

1. 业务能力通过稳定接口暴露，不直接依赖具体编排框架。
2. 将“流程编排”与“领域逻辑”分离，编排只负责步骤串联。
3. Prompt、搜索、模型调用全部走独立服务模块，禁止在编排代码内硬编码。

推荐分层：

1. `Application Service`：对外提供 `chat()` 入口（Controller 仅调用这一层）。
2. `Orchestrator Adapter`：统一编排接口（如 `run_chat_flow(context)`）。
3. `Orchestrator Impl`：当前为轻量函数编排实现；后续可替换为 LangGraph 实现。
4. `Domain Services`：`IntentService`、`QueryService`、`AnswerService`、`SearchService`、`LLMService`。

迁移到 LangGraph 时的最小改动目标：

1. 保持 Controller、API 协议、SSE 事件结构不变。
2. 保持 Domain Services 不变，仅替换 `Orchestrator Impl`。
3. 保持 Prompt 模板仓与配置格式不变，仅修改调用路径。
4. 通过开关配置切换编排实现（如 `ORCHESTRATOR=lite|langgraph`）。

### 1. 前端模块

1. `ChatPage`：对话主页面，承载消息列表与输入区。
2. `MessageList`：区分用户消息和Agent消息，支持来源块渲染。
3. `InputBox`：输入、发送、回车处理、禁用态管理。
4. `Suggestions`：首页推荐问题卡片。
5. `ThinkingIndicator`：处理阶段文案展示（分析、搜索、整理等）。
6. `SSEClient`：消费后端流式消息，处理增量文本与结束信号。

### 2. 后端模块

1. `ChatController`：
   - 校验请求参数
   - 返回SSE响应
2. `ChatOrchestrator`：
   - 意图识别
   - 槽位缺失判断与追问
   - 搜索计划生成与执行
   - 回答生成
   - 来源链接规范化
3. `PromptBuilder`：
   - 构建系统Prompt与任务Prompt
   - 注入能力边界与免责声明规则
4. `SearchService`：
   - fallback 静态知识库查询（替代原搜索引擎通用搜索）
   - 结果去重与基础清洗
5. `LLMService`：
   - 模型调用封装（OpenAI 兼容协议，MiniMax-M2.5-highspeed）
   - 超时、重试、错误分类
   - 思维链过滤（自动去除 `<think>...</think>` 标签）
6. `PlatformAPI`（新增）：
   - 保险平台直连 API 抽象基类
   - 各平台实现：小雨伞、平安、慧择
   - 新增平台只需继承基类并实现 `search()` 方法

## 四、关键流程设计

### 1. 对话主流程（正常路径 — 双通道）

> **架构变更（2026-03-25）**：通道A 从「搜索引擎 site: 限定搜索 + HTML 抓取」改为「平台直连 API」；通道B 的通用搜索改为 fallback 静态知识库；LLM 协议从 Anthropic 切换到 OpenAI 兼容协议（MiniMax-M2.5-highspeed）。

1. 前端（端口 3001）调用 `POST /api/chat` 并建立 SSE 连接（直连后端 8000 端口，不走 Next.js rewrites 代理）。
2. 后端进行意图分析（保险相关性 + 问题类型）+ 预算提取。
3. 若信息充分且为产品推荐/查询/对比类意图，启动**双通道并行**：
   - **通道A（产品卡片）**：调用各保险平台的搜索 API（小雨伞/平安/慧择）→ 获取结构化产品数据 → 预算筛选与排序 → 推送 `products` 事件（含价格）。
   - **通道B（文字建议）**：fallback 静态知识库提供上下文 → LLM 基于知识库生成选购建议 → 通过 `delta` 事件流式推送。
4. 若为知识/条款类意图，仅走通道B（无产品卡片）。
5. 统一拼装尾部：来源列表 + 免责声明 + done。

关键设计原则：
- 产品数据由**平台直连 API** 提供结构化数据（名称、价格、链接），**不经过 LLM**，不经过搜索引擎。
- LLM 仅负责文字分析和建议，不生成链接和价格。LLM 输出的 `<think>...</think>` 思维链在后端自动过滤。
- 两个通道并行执行，产品卡片先于文字回答展示。
- 不再依赖 MiniMax Search API 或 Open-WebSearch MCP 进行产品搜索。
- 详见 [后端专题/05-产品推荐双通道方案-后端.md](后端专题/05-产品推荐双通道方案-后端.md)。

### 2. 追问流程（信息不足路径）

触发条件：

1. 用户问题过于泛化（如“推荐个保险”）。
2. 缺少关键槽位（年龄、预算、保障偏好）。

执行逻辑：

1. 不执行搜索。
2. 直接生成追问话术（1至2个问题）。
3. 输出追问并附简短说明，等待用户补充信息。

### 3. 异常与降级流程

1. 搜索服务失败：
   - 重试一次
   - 仍失败时给出“暂时无法获取最新数据”提示
2. LLM超时：
   - 返回标准化错误消息
   - 保持前端会话可继续
3. SSE中断：
   - 前端提示“输出中断，可点击重试”

## 五、接口设计（阶段一版本）

### 1. `POST /api/chat`

请求参数：

1. `message: string` 用户输入
2. `sessionId?: string` 会话ID（可选，MVP可弱化）

SSE事件建议：

1. `status`：阶段状态更新（分析中/搜索中/整理中）
2. `delta`：增量文本
3. `products`：产品卡片（含价格，由平台直连 API 返回）
4. `products_update`：产品补充信息（可选，通常不推送）
5. `sources`：来源列表
6. `done`：完成
7. `error`：错误

### 2. `GET /api/suggestions`

返回参数：

1. `suggestions: string[]` 推荐问题列表（3至5条）

## 六、Prompt策略设计

### 1. System Prompt核心约束

1. 角色：专业、客观、中立的保险咨询助手。
2. 边界：不销售、不承诺收益、不编造信息。
3. 数据来源：优先基于搜索结果回答，禁止脱离检索臆测。
4. 输出要求：结构清晰、语言通俗、包含免责声明。

### 2. 任务Prompt模板

1. 意图识别模板（问题类型 + 是否缺信息）。
2. 搜索词生成模板（3至5个关键词）。
3. 回答生成模板（基于检索摘要 + 附来源编号）。

## 七、搜索策略设计

### 1. 查询分类

1. 概念解释类
2. 产品咨询类
3. 条款细节类
4. 对比分析类
5. 核保初筛类（仅基础参考，不给最终结论）

### 2. 搜索执行策略

1. 每次查询生成3至5个关键词。
2. 每关键词抓取Top N结果（建议N=10）。
3. 去重规则：按URL主域名 + 标题相似度。
4. 可信度优先：官网、监管/官方机构、主流媒体、专业评测站。

### 3. 结果清洗规则

1. 弱化广告内容与营销软文。
2. 删除信息缺失或明显无关结果。
3. 标记“信息不一致”的结果，生成回答时做风险提示。

## 八、数据与存储策略

阶段一采用“最小存储”：

1. 会话仅保留短期上下文（可内存或轻量缓存）。
2. 不建设本地产品库和向量库。
3. 日志记录脱敏处理，不保存敏感身份信息。

建议日志字段：

1. `requestId`
2. `sessionId`
3. `queryType`
4. `latencyMs`
5. `searchCount`
6. `sourceCount`
7. `errorCode`

## 九、性能与稳定性设计

### 1. 性能目标

1. 首字响应 < 3秒
2. 全量响应 < 15秒
3. 并发能力 50 QPS（压测口径）

### 2. 性能优化点

1. 并行执行多个搜索关键词请求。
2. 控制Prompt长度，减少无关上下文。
3. 启用流式输出，降低用户等待感知。
4. 对热门问题做短期缓存（TTL建议10至30分钟）。

### 3. 稳定性措施

1. 外部服务超时控制（LLM与Search均设置超时）。
2. 指数退避重试（最多1至2次）。
3. 错误分级与统一错误码。

## 十、安全与合规设计

1. 输入输出基础审查（敏感词、违规表述）。
2. 全链路HTTPS。
3. API Key使用服务端环境变量管理，不下发前端。
4. 每次回答附免责声明：
   - “以上信息仅供参考，具体保障内容请以保险合同条款为准。”

## 十一、部署方案

### 1. 部署原则（阶段一最终方案）

1. 仅维护单一 Docker Compose 配置文件：`deploy/compose/docker-compose.yml`。
2. 仅维护单一环境变量模板：`deploy/env/.env.example`。
3. 阶段一不维护 `nginx`，由前后端容器直接暴露端口（前端 3001 / 后端 8000）。
4. 配置差异通过 `.env` 注入，不新增多环境 compose 文件。

### 2. 组件与职责

1. `frontend`：Next.js 容器，提供 Web 对话界面。
2. `backend`：FastAPI 容器，提供 `/api/chat`、`/api/suggestions` 等接口。
3. `redis`：缓存与短期状态。
4. `postgres`：结构化数据存储（阶段一可按需启用）。

### 3. 标准部署命令

```bash
docker compose \
  -f deploy/compose/docker-compose.yml \
  --env-file deploy/env/.env.example \
  up -d --build
```

### 4. 标准停止命令

```bash
docker compose -f deploy/compose/docker-compose.yml down
```

### 5. 运维约束

1. 不在本阶段引入额外网关层，减少维护面。
2. 镜像与配置分离，镜像尽量保持无环境耦合。
3. 发布前检查健康状态与关键指标（响应时延、错误率、SSE中断率）。

## 十二、监控与验收

### 1. 核心监控指标

1. 接口响应时间（P50/P95/P99）
2. SSE中断率
3. 外部API错误率（Search/LLM）
4. 来源覆盖率
5. 回答失败率

### 2. 验收检查点

1. 问答、搜索、溯源、流式均可用。
2. 常见问题集回答准确率达标。
3. 性能指标满足阶段一要求。
4. 异常情况下有可理解的降级提示。

## 十三、已知风险与应对

1. 搜索结果质量波动：
   - 增加来源可信度评分与过滤规则。
2. 模型幻觉风险：
   - 强制“基于检索结果作答”，不确定则明确说明。
3. 响应时延偏高：
   - 并发搜索 + 限制输入输出Token + 流式输出。
4. 合规风险：
   - 固定免责声明 + 规则拦截高风险措辞。
